## Facts this table rests on

- ADOT Lambda layer defaults: `OTEL_PROPAGATORS="baggage,xray,tracecontext"` — composite `extract` runs the propagators in order and later results win, so a carrier's `traceparent` wins over `x-amzn-trace-id` when both are present. The invocation span's parent still prefers the Lambda-supplied `_X_AMZN_TRACE_ID` env var through a separate patch (`instrumentation-patch.ts`), independent of propagator order. Source: aws-observability/aws-otel-js-instrumentation `register.ts` (`setAwsDefaultEnvironmentVariables`), `instrumentation-patch.ts`, opentelemetry-js `composite.ts`.
- Outgoing AWS SDK v3 calls: the Smithy middleware patch injects all propagators into HTTP headers, so `PutEvents` / `SendMessage` carry the X-Ray header. Source: `smithy-send-patch.ts`.
- `@opentelemetry/instrumentation-aws-lambda` ≥0.71.0 adds SQS span links per record from `AWSTraceHeader` or message attributes (`useGlobalPropagatorForSqsExtraction`, not settable by env).
- `@opentelemetry/instrumentation-aws-sdk`: SQS `SendMessage(Batch)` and SNS `Publish` inject into `MessageAttributes`; `ReceiveMessage` adds links; no EventBridge service extension (`services/` has no `eventbridge.ts`).
- EventBridge `TraceHeader`: 1–500 chars, X-Ray format; https://docs.aws.amazon.com/eventbridge/latest/APIReference/API_PutEventsRequestEntry.html
- SQS: `AWSTraceHeader` system attribute overrides the HTTP header, excluded from quotas; https://docs.aws.amazon.com/xray/latest/devguide/xray-services-sqs.html
- X-Ray accepts W3C trace ids since 2023-10, so `formatXrayTraceHeader` may put non-epoch bytes in the `Root` prefix.
- `traceparent` / `tracestate` / `x-amzn-trace-id` in a carrier slot (detail / messageAttributes / `_trace` / payload) are propagation slots, not caller data. When `inject*` writes a fresh span context it removes stale span slots in the other channel: a fresh `traceparent` removes a stale `x-amzn-trace-id` (xray-first readers — xray-only propagators, xray-last configs, and sekimori's own messageAttributes-first SQS extract — would otherwise pick the older context), and a fresh X-Ray context (native `AWSTraceHeader`/`TraceHeader`/`traceHeader`, or an xray-only carrier field) removes a stale `traceparent`/`tracestate`, which would otherwise win under the ADOT composite order (`tracecontext` extracts last).
- Stale span slots are scrubbed only when a fresh span context is written. A baggage-only inject adds entries without touching span slots (augment, don't re-root): a carrier that already pins `traceparent`/`x-amzn-trace-id` keeps it, and under the ADOT order a pinned `traceparent` wins over any injected X-Ray context. To control which context propagates, pass `options.context` rather than pinning carrier keys.
- Producer and consumer are expected to share propagator coverage. An xray-only producer writes only `x-amzn-trace-id`; a w3c-only consumer cannot read it back (no carrier key it inspects). `parseXrayTraceHeader` is deliberately lenient — it accepts headers without `Sampled`, which `AWSXRayPropagator.extract` rejects — so the SQS `AWSTraceHeader` fallback covers slightly more inputs than the carrier path.
